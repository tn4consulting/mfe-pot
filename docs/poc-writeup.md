# MFE Proof of Technology — Writeup

> **Scope note**: this is an independent proof-of-technology exercise, built as a personal/consulting exploration of micro-frontend architecture. It is not affiliated with, endorsed by, or associated with Service Canada, ESDC, or the Government of Canada. "MSCA" and GC design-system references exist only to ground the architecture in a realistic scenario. This document is a retrospective — what was built, why, what it proved, and what it cost to learn. For living architecture reference, see `mfe-pot-platform/CLAUDE.md`; for the repo map, see `../CLAUDE.md`; for outstanding work, see `TODO.md`.

## Summary

Over roughly one week (2026-08-01 to 2026-08-07), a single Nx/Angular monorepo proving out micro-frontend (MFE) architecture for a fictional "My Service Canada Account" (MSCA) scenario was carried through five major transformations: it was split into independent per-app repositories with strong published-package contracts; its hosting model moved from static Firebase Hosting to containers on Kubernetes; its frontend framework was migrated wholesale from Angular to React; its design system was rebuilt from a GC-owned wrapper (GCDS) into a self-contained in-house one (SCDS); and a second, independently-branded host app was scaffolded to prove the federation pattern generalizes beyond a single "shell." What started as one repo is now **7 independent repos** — a platform repo, two host apps, and four federated domain remotes — each independently buildable, testable, and deployable, sharing infrastructure (a mock OIDC identity provider, a headless CMS acting as both content store and live federation directory) but not a build.

The architecture claim under test was narrow and mechanical: *can independently-deployed frontends, owned by different teams/repos, compose at runtime into one coherent, accessible, bilingual citizen experience — and can that same pattern support more than one front door?* That claim held up under real (if local) verification: runtime remote loading, cross-remote widget embedding, graceful degradation on remote/service failure, live directory updates with no rebuild, a second host app sharing the same platform infrastructure, and end-to-end PKCE authentication verified independently by three separate backends. The *demo/policy narrative* the architecture was meant to eventually carry — a "tell us once" story showing a life-event-organized experience beats a siloed one — was deliberately not built; it remains the single largest gap between what exists today and what the original design set out to prove.

A follow-on push on 2026-08-08 shifted focus from proving the architecture to proving it survives contact with production concerns: the planned cloud target changed from Azure/AKS to a real AWS EKS account (applied and live-verified, not just IaC written), a full OpenTelemetry tracing/metrics stack was built and confirmed working end to end on both `kind` and EKS with an explicit client-impact-resilience guarantee, and the first real governance tooling for a solo-built system that's about to become seven teams' worth of code landed as a published, version-drift-catching package. None of this changes the mechanical architecture claim above — it was already proven — but it closes a real gap between "proven on a laptop" and "proven somewhere a citizen could actually reach it."

The next day (2026-08-09) added a third dimension to the "does this pattern generalize" question — not just more hosts (08-07) but more *journeys within a single remote*: `mfe-pot-employment-life-events-mfe` was generalized and renamed to `mfe-pot-life-events-mfe`, turning one hardcoded "you lost your job" checklist into a small internal schema (a discriminated-union `LifeEventSection` kind, plus an explicit escape hatch for a life event whose UI genuinely needs to diverge) that now drives three life events — job loss, birth, disability — from one federated remote, fronted by a new shell-owned `/life-events` hub page.

## Final architecture

**7 repositories**, none of them git submodules — independent sibling clones under `github.com/tn4consulting`, tied together locally only by a VSCode multi-root workspace file and this meta repo's coordination docs:

| Repo | Role |
|---|---|
| `mfe-pot-platform` | Shared libraries (`@tn4consulting/shared-*` published packages), the composed `mfe-e2e` Playwright suite, Strapi (CMS + federation directory), the mock IdP, the two Helm library charts. |
| `mfe-pot-msca-shell` | Host app #1 — MSCA branding, composes all 4 remotes, sidebar nav. |
| `mfe-pot-job-bank-shell` | Host app #2 — minimal, single-remote proof that the pattern generalizes beyond one host. |
| `mfe-pot-dashboard-mfe` + `dashboard-bff` | Cross-benefit overview, payment history, correspondence. |
| `mfe-pot-job-bank-mfe` + `job-bank-bff` | Job search and apply. |
| `mfe-pot-employment-insurance-mfe` + `employment-insurance-bff` | EI application, claim status, reporting. |
| `mfe-pot-life-events-mfe` | Multi-life-event guided journeys (job loss, birth, disability today) stitching the other three apps together, one per life event via a shared schema-driven kit. |

**Stack, as it stands today**: React (migrated from Angular), Native Federation (`@softarc/native-federation`, esbuild-based — not Nx's webpack-based Module Federation tooling, which has no first-class support for it), a self-built design system (SCDS, replacing the GC Design System), Strapi for bilingual CMS content and the live federation directory, Express BFFs behind each domain remote that needs one, a real OIDC-shaped mock identity provider (authorization-code + PKCE, RS256-signed JWTs, independently verified by every BFF), Kubernetes via Helm — proven on `kind` for the whole family, and since applied to a real AWS EKS cluster (the cloud target changed from an originally-planned Azure/AKS, for account-management reasons, not technical ones), live-verified for a representative subset of workloads — OpenTelemetry tracing/metrics (an OTel Collector, Tempo, Prometheus, Grafana, two published shared packages) across all 7 repos, and pnpm/Nx per-repo tooling. No shared build system ties the 7 repos together; alignment is enforced by convention (`platform-versions.json`), Renovate grouping, semver on published packages, and — new as of 08-08 — an actual automated version-drift check (`shared-platform-standards`), not just convention.

## Key design decisions

### 1. Runtime federation, never compile-time composition
Every remote is loaded dynamically via Native Federation's runtime manifest (name → URL + version), not bundled into a host at build time. This was the load-bearing decision the whole PoT exists to test, and it held: a host reads a manifest and mounts what it finds, so redeploying one remote never requires rebuilding another. Two federation patterns were proven, not just one — (a) a routed component the host mounts on navigation, and (b) standalone cross-remote widgets (`dashboard`'s payment-history widget embedded live inside `life-events`; similar widgets exposed by job-bank and employment-insurance).

### 2. Minimal federation-sharing surface, weighed explicitly each time
The policy from day one: default to *not* sharing a library as a federation singleton, because every shared entry re-couples independently-deployed apps' version schedules — the opposite of the point of the exercise. Only large, stable, low-churn dependencies (or things whose entire purpose is cross-boundary *identity*, not just behavior) clear that bar. Today that's `react`/`react-dom`, the design system's core package, and — non-obviously — the shared federation-runtime package itself, because its React Context objects need identical object identity across every app that provides or consumes a cross-remote widget loader. Everything else (auth session, active locale) crosses boundaries as a small versioned DTO plus a broadcast event instead, deliberately kept out of the shared-singleton surface.

### 3. Host-mediated cross-remote composition, not remote-to-remote
A remote calling into another remote directly doesn't work under Native Federation as deployed here — each remote bundles its own disconnected copy of the federation runtime, so a nested load call just hangs. The fix adopted architecture-wide: the host (which always has a working federation runtime) resolves the widget and hands it down via a React Context every consuming remote can read. This is a real constraint of the framework, not a stylistic choice, and it shaped how every widget in the system is built.

### 4. Strong contracts across repo boundaries via published packages, not shared source
Once the monorepo split, the only thing holding the 6 app-owning repos together is `npm`/GitHub Packages semver: shared libraries publish as versioned `@tn4consulting/shared-*` packages with real `.d.ts` output, and a breaking change requires a major bump — a consumer that hasn't updated simply fails to build. This is the direct, deliberate answer to "how do you keep 7 repos from silently drifting apart": no compile-time cross-repo safety net exists (Native Federation's shared-singleton contract fails at *runtime* on version drift, with no build-time warning), so the discipline lives in the publish/version step instead.

### 5. BFF-per-domain, applied only where it earns its keep
Not every remote got a backend. `job-bank` and `employment-insurance` each got a small dedicated BFF because that's the realistic shape of those systems and because job-bank's components specifically needed to work outside this shell too (a real API, not client-side mock state). `dashboard-bff` composes a cross-benefit overview by calling the other two BFFs over real HTTP with an explicit partial-failure contract (a slow/failed upstream degrades only its own tile, never the whole response) — composition over real service calls, not by importing another domain's in-memory state, which is what actually makes the "these are independently deployed" claim true rather than asserted. `dashboard`/MSCA-D and `life-events` deliberately got no BFF of their own — there was no distinct bounded context to justify one.

### 6. Defense-in-depth security, not shell-mediated trust
Sign-in is a genuine authorization-code + PKCE flow against a real (if mock) OIDC-shaped identity provider — one-time codes, RS256-signed JWTs, a JWKS endpoint — not a one-click stub. Every BFF independently verifies the bearer token against the IdP's JWKS, and every remote checks its own claims rather than trusting that "the shell let me navigate here" is sufficient authorization. This was verified concretely: a remote hit directly at its own origin, with no shell and no session, blocks its own content on its own.

### 7. Environment-swappable everything, converging on runtime config
Content (`ContentClient`), the federation directory (`RemoteRegistryProvider`), and environment values (BFF URLs, feature flags) all follow the same shape: an interface with a live-backed implementation (Strapi, a container-injected ConfigMap) and one or more fallback implementations (static baked JSON, in-memory stubs for tests), selected by configuration rather than code changes. This pattern, established for content in the original design, was later generalized to environment config itself when hosting moved to Kubernetes — one mechanism (`window.__mfePotEnv`, written by a container entrypoint script from a Helm-supplied ConfigMap) replaced the old Angular build-time `fileReplacements` swap entirely.

### 8. Two front doors, one shared platform
The second host app (`mfe-pot-job-bank-shell`) was built specifically to test whether "runtime federation host" is a reusable pattern or an artifact of having only ever built one. It shares the same `mock-idp` and Strapi instance as the original MSCA shell, composes a single remote with no sidebar nav (nothing to navigate between), and has its own distinct branding, PKCE client, Ingress host, and Helm release. This is the closest the PoT gets to the real-world shape it's modeling — Job Bank and MSCA genuinely are separate government properties that happen to share underlying services.

### 9. Naming as a deliberate signal, not an afterthought
Once two host apps existed, `job-bank-shell.mfe-pot.local` (the host) and `job-bank.mfe-pot.local` (the remote it composes) were one hyphen apart and easy to misread as the same thing. The resolution: front doors — what a citizen would actually see — keep plain brand names (`msca.mfe-pot.local`, `job-bank.mfe-pot.local`); every internal federated remote gets an `-mfe` suffix cascaded through its Ingress host, repo/directory name, Nx project name, federation identity, Docker image, and Helm chart/release. Business-domain naming (BFF names, `scope:*` tags, CMS content keys, route paths) deliberately stayed un-suffixed, since that identity has nothing to do with hosting and there was no collision to resolve there.

### 10. Telemetry is defense-in-depth too: it must fail open, never closed
The same posture behind decision 6 (every BFF verifies its own auth independently) was applied to observability: `initNodeObservability`/`initBrowserObservability` wrap their own SDK setup in try/catch and log-and-continue rather than throw, specifically so a broken or unreachable telemetry backend degrades visibility, never the citizen-facing request. This was verified, not just written — scaling the OTel Collector to zero replicas and hitting a real BFF fan-out repeatedly produced identical latency and zero errors. A tool that exists to catch failures shouldn't be able to cause one.

### 11. Governance as a published, versioned artifact, not a document
Once a solo-built system was about to become seven teams' worth of code, the instinct to write a "standards" doc and trust everyone to read it was deliberately rejected in favor of the same mechanism already trusted for everything else cross-repo: a real `npm`-published, semver-versioned package (`shared-platform-standards`) that *runs* a version-drift check in CI rather than describing one. It paid for itself immediately — piloting it surfaced real, previously-invisible drift (stale `shared-ui-scds-core`/`shared-federation-runtime` pins) in nearly every app repo despite `platform-versions.json` and Renovate already existing. Convention alone hadn't been enough; a periodic automated check was.

### 12. A schema with a deliberate escape hatch, not a rewrite per variant
Generalizing `life-events` from one hardcoded journey to three could have meant either a rigid one-size-fits-all template (breaks the moment a journey genuinely needs something different) or a full bespoke component per journey (no shared plumbing at all, the same problem the original design was trying to avoid one level down). The resolution: a small discriminated-union schema (`checklist` / `links` / `widget` / `custom` section kinds) covers the common shape, and `custom` is a first-class, no-apology way for a section to fully opt out and supply its own render function. `birth` needed zero kit changes; `disability`'s multi-step stepper used the escape hatch — proving the schema doesn't buckle under the first case that doesn't fit its assumptions, which is usually where this kind of internal generalization quietly fails.

## What was proven

- **Independent runtime composition**: a host discovers and loads remotes at runtime from a live directory; stopping one remote degrades only its own route/widget, never the whole host.
- **Cross-remote widget embedding**: a component owned by one independently-built, independently-deployed remote renders live inside another remote's page, sourced with real (if mock) data.
- **Live directory updates with no rebuild**: editing a "Remote" entry in Strapi's admin and reloading picks up the new URL/version immediately.
- **Partial-failure degradation**: killing a dependency BFF degrades exactly the tile that depends on it, confirmed by directly killing pods and observing the response shape change from `ok` to `unavailable`.
- **Independent testability**: every app builds, serves, and tests standalone with stub auth/locale/registry, with no dependency on the shell or any sibling being up.
- **Bilingual switching across federation boundaries**: toggling language updates both the host's own chrome and an independently-loaded remote's chrome simultaneously, off one broadcast event each app subscribes to independently.
- **End-to-end PKCE authentication, independently verified three times**: a citizen's session, established once against the mock IdP, is independently validated by every BFF against the IdP's JWKS — no shared secret, no shell-mediated trust.
- **Real cross-repo, cross-Helm-release service traffic**: `dashboard-bff` calling `job-bank-bff`/`employment-insurance-bff` over in-cluster Kubernetes Service DNS, confirmed live, not just asserted.
- **The pattern generalizes to a second host**: two independently-branded, independently-deployed shells share one platform's infrastructure with zero required changes to the platform repo itself.
- **WCAG 2.2 AA**, verified with automated `axe` scans on every route, currently zero violations.
- **The architecture survives real cloud infrastructure, not just `kind`**: AWS EKS applied to a live account (`ca-central-1`), with real HTTPS via cert-manager, real DNS via Route 53/external-dns, and real cross-service connectivity (Redis, mock-idp's JWKS endpoint) confirmed for a representative pair of workloads (`mock-idp`, `job-bank-mfe`).
- **Distributed tracing across independently-deployed, independently-owned BFFs**: a single citizen action (`GET dashboard-mfe.../api/overview`) produces one trace ID spanning `dashboard-bff` → `job-bank-bff` and `dashboard-bff` → `employment-insurance-bff`, each BFF's own Redis calls included — confirmed live on both `kind` and the real EKS deployment.
- **Telemetry failure doesn't become citizen-facing failure**: killing the OTel Collector entirely produced zero latency or error impact on real BFF traffic, confirmed live, not just asserted from the code.
- **An automated cross-repo drift check actually catches drift that convention alone missed**: rolling out a version-enforcement package to all 6 app repos immediately found real, previously-invisible mismatches against `platform-versions.json`'s pinned versions in nearly every one of them.
- **The federation pattern generalizes to multiple journeys sharing one remote, not just multiple hosts**: `life-events-mfe` now authors three distinct life events (job loss, birth, disability) from one schema-driven kit with one federated identity, including a divergent multi-step UI (disability) proven through the schema's own escape hatch rather than a special case bolted on beside it. Build/test/lint green and CI's `kind`-validation (image build + Ingress curl check) passed for both the remote and the shell's new `/life-events` hub page; not yet separately confirmed with a manual browser pass the way the three federation-adjacent production bugs elsewhere in this doc required.

## What was not proven / deliberately deferred

- **The policy/demo narrative** — the "before/after" siloed-vs-life-event story, a visible "tell us once" data-sharing beat, a journey-outcome meter, a "show the seams" federation overlay, a repeatable demo runbook. This is architecturally blocked on a real gap: the shared "tell us once" service (`client-profile-service`) was removed mid-project when its one caller stopped needing it, and its data folded into `dashboard-bff`'s own local store — which `job-bank-bff`/`employment-insurance-bff` can't reach. The demo narrative needs a real cross-BFF shared store before it can be built, not just wiring.
- **Sustained concurrent load** against the shared mock IdP/Strapi from two hosts — only exercised under light manual/CI traffic.
- **A host composing more than one remote while staying minimal-scope** — the second host deliberately stayed single-remote to keep the proof narrow.
- **AKS/ACR** — superseded, not built: the cloud target moved to AWS EKS instead (see "What was proven"), for account-management reasons, not technical ones.
- **A fully-populated AWS EKS cluster** — CI (`deploy-eks`) is wired and pushed for all 8 chart-owning repos, but only `mock-idp` and `job-bank-mfe` have actually been deployed and live-verified there; the other 7 workloads' EKS path is CI-ready but not yet exercised end to end.
- **Browser-to-BFF trace propagation** — OpenTelemetry's server-to-server leg (BFF calling BFF) is verified live; the browser leg (a real deployed frontend generating its own `traceparent` via `propagateTraceHeaderCorsUrls`) has only been exercised with a hand-crafted payload, not from an actual browser session.
- **Backend-outage resilience** — design only, no code: degraded-read serving, per-domain staleness rules, client-side write queueing for offline submissions, and circuit-breaker health signaling are all specified (`docs/plans/20260808-1800-backend-outage-resilience.md`) but not started.
- **Multi-team governance process** — beyond the automated version-drift check (built, published, rolled out), CODEOWNERS, CONTRIBUTING.md, PR/issue templates, an ownership map, and the breaking-change/deprecation protocol are all still design-only.
- **The composed end-to-end suite covering all 5 apps** — `mfe-e2e`'s `webServer` array currently starts nothing, since its one hard dependency (`client-profile-service`) was removed; it needs rewiring to each sibling repo's checkout.
- **Cree/Inuktitut support** — scoped and investigated (including a hard ceiling found in the GC Design System's own bilingual-only internals, before that dependency was later removed entirely), but not built.

## Lessons and learnings

### On micro-frontend federation specifically
- **A framework migration (Angular → React) genuinely simplified the federation story**, not just the component code. Angular's DI-tree-per-remote design required each remote to export its own `REMOTE_PROVIDERS`, needed `ENVIRONMENT_INITIALIZER` instead of `APP_INITIALIZER` (which silently never fires for a child environment injector), needed re-providing singleton services per environment injector, and needed a `component`+`providers` pairing for widget loading. React remotes mount directly into the host's existing tree with no second root and no DI tree to populate — each remote just fetches its own config and constructs its own client on mount. This wasn't a mechanical port; the React version is structurally simpler because the framework has less machinery for the host to have to reason about.
- **Federation-adjacent bugs hide from every automated check and only surface in a real composed browser session.** Three separate times, work that was fully green on `lint`/`test`/`build` (and, worse, on `nx serve` in dev mode) broke in an actual browser or in a real production build: a missing `share()` entry for a Stencil component library's `/loader` subpath silently failed only the composed remote, not the host or any standalone test; layout CSS in a remote's own stylesheet silently never loads once that remote is federated into a host (only Shadow-DOM-encapsulated component styles survive; plain CSS classes need to become inline styles); and a minified shared React chunk crashed at runtime in a real production build in a way `nx serve`'s dev-mode build never exercised, hiding in every app since its own React conversion until a live `kind` deployment finally ran an actual production build path. The standing rule this produced: **verify in an actual browser against a real composed deployment, not just green CI**, before calling federation-adjacent work done.
- **A shared library that isn't marked `external`/`shared` correctly can silently bundle its own disconnected copy of a stateful package**, with no error — just a `federationPromise` (or a React Context) that never resolves the way the rest of the app expects. This bit both `native-federation` itself (a plain library importing it directly instead of via an injected loader) and, separately, a host's own hand-written non-federation-managed entry bundle omitting a package from its own `external` list. The fix pattern was the same each time: route dynamic loading and shared state through an explicitly shared package/Context, never a direct import from a place the federation tooling doesn't already control.
- **Cross-remote composition cannot be remote-to-remote under this tooling** — it has to be host-mediated, because each remote's federation runtime is its own disconnected instance. This is a real architectural constraint of the framework choice, not a design preference, and it shaped every widget-embedding feature built.

### On the polyrepo split and cross-repo contracts
- **Tighten enforcement (module boundaries, dependency constraints) *before* splitting, while a violation is still a one-PR fix.** Doing this ahead of extraction caught a real violation (a host with a compile-time import into a to-be-separate repo's library) that would otherwise have become a cross-repo rewrite after the split.
- **A published package's runtime shape (ESM vs. CJS, `"type": "module"`) needs to be gotten right once, or every consumer repeats the same fix.** Every extracted repo independently hit the same Jest CJS/ESM resolution failure against published `@tn4consulting/shared-*` packages and needed the identical `transformIgnorePatterns` fix — a cost paid five times because it wasn't fixed at the source once.
- **Extraction gotchas compound in predictable, avoidable ways when copy-pasting a "proven" template.** Missing `.tool-versions`/`pnpm-workspace.yaml` files in a copy-pasted extraction silently fell back to the wrong Node version, producing an error message that looked exactly like an unrelated ESM/federation bug — a case where a correct-looking error message pointed at entirely the wrong root cause. Worth a checklist, not just "copy job-bank's files."
- **A stale reference to a removed project doesn't fail softly.** An Nx `implicitDependencies` entry pointing at a project that no longer exists breaks the entire project graph, not just the one affected target — a hard failure mode worth knowing before removing any project from a still-shared workspace.
- **Semver-enforced contracts genuinely substitute for compile-time cross-repo safety, except at the one seam that matters most.** Once native federation's shared-singleton version pinning is involved, a mismatch across independently-versioned repos fails silently at *runtime*, with no build-time signal at all — the one place where "the type system will catch it" doesn't apply, and the one place a periodic live version-alignment check (reading each deployed remote's own `remoteEntry.json`) was flagged as the real fix, not yet built.

### On infrastructure and tooling
- **Environment quirks masquerading as application bugs cost real time.** A Docker daemon reporting an old cgroup version broke `kind` cluster creation outright against its default node image (fixed by pinning an older image); what looked like registry flakiness during a slow `pnpm install` turned out to be unrelated containers from other projects starving Docker Desktop of memory; a hung `nx` postinstall script (despite its own internal watchdog) turned out to not be worth chasing to root cause once a simple config change (excluding it from `onlyBuiltDependencies`) sidestepped it entirely. The pattern across all three: confirm the actual failure boundary (host environment vs. build config vs. application code) before assuming the newest change is the cause.
- **A static image tag plus `pullPolicy: Never` gives Kubernetes no signal to redeploy a pod when only the underlying image content changes.** Every local deploy script in the family now force-restarts affected pods explicitly after a rebuild — and the one time this step was missing for one service (Strapi, after an otherwise-unrelated change touched its seed data), the gap silently served stale data for two-plus days before a live verification pass caught it by checking actual served content, not just that the hostname returned 200. The general lesson: **"deployed" and "verified" are not the same claim** — curl-level checks confirm a container serves *something*, not that it's the *current* something.
- **Non-secure-context browser APIs (like `crypto.subtle`) are absent on more real deployments than "developing on `localhost`" suggests.** PKCE's S256 challenge computation needs `SubtleCrypto`, which doesn't exist on plain-HTTP non-`localhost` hostnames — exactly the shape of every `kind`-deployed hostname in this project. The fix (a documented `plain`-method fallback already in the PKCE spec) existed the whole time; the gap was assuming "not literally `http://` from a user's perspective" was the same test as "secure context," which it isn't.
- **A stale CI check doesn't fail loudly — it fails by quietly not catching the thing it exists to catch.** `mfe-pot-life-events-mfe`'s `kind-validation` step grepped a deployed page for `<msca-le-root`, an Angular-era element this now-React app never renders — so the check always "passed" (found nothing wrong because it was checking for the wrong thing entirely) while a genuinely broken EKS release, months old, sat pointed at a `kind`-only hostname undetected. `lint-test-build` staying green made this easy to miss; the fix was making the check assert something that would actually fail on the real bug (`<script src="env.js">`, the pattern already used elsewhere in the family).
- **Cloud IAM trust policies should be verified against a real decoded token, not a tutorial's example format.** AWS/GitHub OIDC federation failed with a generic "Not authorized" despite an apparently-correct trust policy; the actual `sub` claim this org's tokens carry (`repo:tn4consulting@<owner_id>/<repo>@<repo_id>:ref:refs/heads/main`) doesn't match the classic `repo:ORG/REPO:ref:refs/heads/BRANCH` format most examples show. Decoding a real token (via a temporary debug CI step) found the actual shape in minutes; guessing from documentation would not have.
- **A managed Kubernetes cluster's default node security group is not "open to the cluster" by default.** EKS's own node security group only opens specific known ports (kubelet, coredns, webhooks, ephemeral return traffic) — not arbitrary pod-to-pod traffic below port 1024. This surfaced as ingress-nginx timing out reaching a frontend pod's port 80 on a different node while the same request to a BFF on port 3001 (inside the ephemeral range) worked — a symptom that looked like an application bug until the actual port ranges were checked.
- **Publishing a genuinely new package needs a manual, per-package grant even with a working org-wide token.** `shared-platform-standards`'s first publish 403'd twice with a scope error despite a correctly-configured `NPM_READ_TOKEN` PAT — every previously-published `@tn4consulting/*` package already had a one-time "Manage Actions access" grant on GitHub, but a brand-new package doesn't inherit it. The PAT's own scope wasn't the problem; a package-level allowlist entry was.
- **A shared `tsconfig.base.json` distributed as a real package and consumed via `extends` doesn't survive Native Federation's build tooling.** `@softarc/sheriff-core` throws once the extended config resolves into `node_modules` rather than living in-repo, for every app repo, not just one — discovered piloting the shared-standards package. The fix was to ship it as a documented reference file instead of a real `extends` target, keeping each repo's own inline `tsconfig.base.json` as the source of truth.
- **`tsc --build`'s real type-checking catches bugs `ts-jest`'s transpile-only mode doesn't.** Building the two new observability packages with a real compile step (rather than relying on Jest's looser per-file transpilation) caught two genuine type errors before publish — a reminder that a green test suite and a type-correct package aren't the same claim.

### On working with the user / process
- **Framing ("this is a proof-of-technology, not a production build") is a real, load-bearing decision, not throat-clearing.** It licensed leaving hardcoded mock transactional data (job postings, claim records, payment amounts) alone while still holding real citizen-facing UI chrome to a genuine bilingual/accessibility bar — a distinction confirmed explicitly when asked, and one that would otherwise be easy to over- or under-scope on a "make this bilingual" request.
- **A design decision revisited under new information (Angular → React, GCDS → SCDS, Firebase → Kubernetes, AKS → EKS) is not the same as an unstable plan.** Each reversal in this project was driven by a concrete discovery or constraint (Angular's federation machinery being genuinely more complex than the framework-agnostic alternative; GCDS being built for static content pages, not an authenticated portal; Firebase Hosting being unable to run the CMS the design depended on; the target Azure account being unmanageable, a non-technical but entirely legitimate reason to move to AWS) — the pattern worth keeping is documenting *why* a decision changed in the same living doc, not just what changed, so the record stays a true account of intent rather than drifting into an aspirational one.
- **"Fully verified" needs an explicit qualifier for what was actually checked.** The single biggest recurring correction across this project's own planning docs was walking back a "fully verified live on kind" claim to "build/serve-verified, not runtime-verified" once real browser bugs were found that curl-level checks couldn't have caught. The same discipline carried into the cloud-hosting push: EKS is described as "CI wired for all 8 chart-owning repos, live-verified for 2 of them" rather than "deployed to AWS," because those are different claims and only one of them was actually checked. Stating the verification method alongside the claim, not just the claim, is what made both corrections possible instead of hidden.

## Where this leaves things

The mechanical architecture claim — independently-deployed, independently-versioned frontends composing at runtime into one coherent experience, generalizing to more than one front door — is proven, verified live, and documented. Two pieces of infrastructure maturity that were open questions as of 08-07 are no longer: real cloud hosting (AWS EKS, applied and live-verified, if not yet for every workload) and real observability (distributed tracing across independently-deployed BFFs, verified fail-open) both exist now, not just as plans. What remains is a mix of finishing that infrastructure push (a fully-populated EKS cluster, the browser leg of tracing, backend-outage resilience code), building out the governance process the version-drift tooling was the first piece of (CODEOWNERS, CONTRIBUTING.md, the breaking-change protocol), and the demo/narrative layer that turns "the pattern works" into "here is why the pattern matters" — which still needs one real design decision (a genuine shared cross-BFF data store) before it can be built at all.
