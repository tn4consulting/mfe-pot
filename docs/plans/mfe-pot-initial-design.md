# Government of Canada MFE Proof of Technology — Design & Scaffold

> Planning document. Original design approved 2026-08-01; kept updated as architecture decisions evolve (see "Updates Since Initial Approval" below) rather than left as a point-in-time snapshot — unlike other one-off documents in `docs/plans/`, which stay timestamped and static. Not citizen- or contributor-facing reference documentation. `CLAUDE.md` is the durable, current summary of the architecture; this document carries the fuller rationale and history behind it.

## Context

The user wants a proof-of-technology (PoT) monorepo demonstrating micro-frontend (MFE) architecture built with Angular, following Government of Canada design/accessibility/bilingual standards. The repo (`mfe-app`) is currently empty. The monorepo is a starting point only — it is expected to be split into separate repos per MFE later, so boundaries between apps must stay clean and loosely coupled from day one.

To ground the PoT in something realistic, it's framed as an ESDC ("job loss support") scenario — **this is fictional scaffolding to give the architecture real shape, not a production build**. GC design/accessibility/bilingual standards are followed faithfully because proving those out *is* the point of the exercise, but authentication and citizen data are deliberately mocked/simplified — there is no real IdP, no real PII, no compliance/security hardening in scope here.

### Apps
- **shell** — the host application, branded as a mock of **"My Service Canada Account" (MSCA)**, the real GC citizen portal that aggregates ESDC/Service Canada benefits — this is the fictional identity for the composed experience: app frame, GC header/footer, language switcher, a stubbed Sign-In-Canada-style mock login, and the runtime federation manifest reader that mounts each MFE
- **dashboard**, branded **"MSCA-D"** — common cross-benefit components: a 360° cross-benefit overview (benefits the person is eligible for, active applications — including job applications that actually originate in `job-bank` — and "my tasks"/actions required), payment history, correspondence history, "tell us once" maintenance (personal details, change of address, change of bank details)
- **job-bank** — job search and **apply for a job** functionality
- **employment-insurance** — EI benefit access and administration: **apply for Employment Insurance**, claim status, and **submit an EI report**
- **employment-life-events** — a client-centric "you lost your job" guided experience that stitches the other three together (CV guidance, job search prompts, EI application guidance, EI reporting reminders)

### Key architecture decisions (confirmed with user)
- **Nx** monorepo tooling
- MFEs loaded **dynamically at runtime as remotes**, never compiled into the host — via **Native Federation** (`@angular-architects/native-federation`, esbuild-based, matches Angular's modern default builder) with a runtime **federation manifest** (JSON) mapping remote name → URL + route prefix, so redeploying a remote never requires rebuilding the shell, and the shell can build routes/deep-links without hardcoding remote route shapes
  - **Risk flag**: Nx does not have first-class Native Federation support today — Nx's built-in Module Federation tooling is webpack-based. Wiring Native Federation into Nx means using `@angular-architects/native-federation`'s own builder/dev-server per project instead of Nx's MF generators. This is feasible but is the single biggest technical unknown in this plan — treat it as a day-one spike, not a settled detail
- **Prove two federation patterns, not just one**: (a) each MFE exposes a routed module the shell lazy-loads, and (b) `dashboard` additionally exposes **one standalone shared widget** (a payment-history component) that `employment-life-events` dynamically imports and renders inline — this is the harder, more valuable MFE capability worth proving out, since it's what "common components used across services" actually implies. Scoped to one widget deliberately, to prove the pattern without multiplying risk; more widgets are a natural extension once it works
- **General federation-sharing policy**: default to *not* marking a library as a federation "shared" singleton. Every shared entry re-couples the apps' deploy/version schedules — the opposite of the independence goal — so it's only worth it for dependencies that are large, stable, and low-churn enough that the coupling cost is clearly repaid. In this workspace that bar is met by **Angular core + RxJS** (also required for the widget-embedding case to work at all) and nothing else. It is explicitly *not* met by feature/business-logic libraries, or by things that change often — which is exactly why the mock auth session and active language cross remote boundaries as a small versioned DTO plus a lightweight event/broadcast mechanism instead of a shared singleton, even though sharing those libs directly would be technically simpler. Any future candidate for sharing should be weighed against this same bar before being added
- Each remote exports its own `REMOTE_PROVIDERS` (HTTP client, interceptors, its Transloco scope) applied both at its standalone bootstrap and on the routes/providers the shell mounts — a lazy-loaded remote route does not inherit the host's provider tree for free
- Remote load failures are handled explicitly in `federation-runtime` (a failed dynamic import degrades just that route/widget, not the whole shell) — this is required for the "stop one remote, others keep working" proof to actually hold up
- **Each MFE's real functionality lives in publishable feature libraries, not in the app itself** — `apps/<name>` is a thin federation host (bootstrap, routing table, DI wiring, federation exposes), while `libs/<name>/feature-*` and `libs/<name>/ui-*` hold the actual components/business logic. This is driven by a concrete future requirement: Job Bank's components need to work both federated into this shell *and* on the standalone real-world Job Bank site, which won't share this shell's auth/i18n/GCDS wiring at all. Structuring every MFE this way (not just Job Bank, for consistency) means the feature libraries could later be re-packaged as an npm library, embedded in a different host, or split into their own repo, without rewriting the functionality — only the thin host wrapper changes
- To make that re-packaging real rather than aspirational, feature libraries depend only on **injected abstractions (DI tokens)** for cross-cutting concerns — identity/session, active locale, telemetry — never on this shell's concrete `auth`/`i18n` implementations directly. `apps/<name>` wires the concrete implementation in; a different host (e.g. the standalone Job Bank site) would wire in its own
- No real backend — integration tests mock everything locally (MSW + a local CMS container)
- Page **content** is bilingual and CMS-driven via a pluggable content-service abstraction, backed by a self-hostable open-source headless CMS integrated for local demos — **Strapi** (strong built-in locale support, Docker-friendly)
- UI **chrome** text uses **Transloco** for runtime, per-MFE translation loading and language switching without reload
- **GC Design System** (`@cdssnc/gcds-components`) web components for all UI
- Accessibility target: **WCAG 2.2 AA**, enforced with automated axe checks in integration tests, not just documentation
- Unit tests: **Jest**. Integration/e2e: **Playwright**, run locally against MSW stubs and the local Strapi container
- Package manager: **pnpm**
- Identity/session: **shell-owned mock SSO** — the shell performs a stubbed Sign-In-Canada-style login, then passes the resulting (mock) authenticated user token to each remote as data (an injected DTO at mount time), not as a shared singleton service instance
- **Each app enforces its own security, defense-in-depth style** — an app must not assume "the shell let me navigate here, so I'm authorized." Each remote independently validates the token it's handed and runs its own route guards/permission checks against its own domain's claims (e.g. `employment-insurance` checks for an EI entitlement claim itself). The token-parsing/validation logic is a plain shared library (`libs/shared/auth`) that each app bundles its own copy of — it's pure/stateless logic, not runtime state, so per the sharing policy above it doesn't need (and shouldn't be) a federation singleton
- **Independent testability is a first-class requirement, not just a consequence of the architecture** — every app must be buildable, serveable, and testable entirely on its own, using stub implementations of whatever it's normally handed (auth token, active locale, remote registry entries), without the shell or any sibling remote running. The composed `mfe-e2e` suite proves the apps work together; each app's own standalone tests prove it doesn't accidentally grow a hidden runtime dependency on being hosted inside the shell
- **Minimize cross-MFE shared state overall** — independence is the point of this architecture, so shared runtime state is treated as a liability to justify, not a convenience to reach for. Today that's deliberately limited to: the Angular/RxJS singleton (structural necessity), the auth token DTO, and the active locale. Any future proposal to share more should be checked against this and the sharing-policy bullet above
- "Tell us once" data (personal details, address, bank details, correspondence history) is served by its own small dedicated backend, **`client-profile-service`**, rather than a shared in-memory library — this matters for correctness, not just consistency: if it were an in-memory lib imported by multiple independently-built remotes (and it isn't a federation singleton, per the sharing policy above), each remote would silently get its own disconnected copy of "the profile," which would quietly break the exact "tell us once, one source of truth" behavior it's meant to demonstrate. A real HTTP-backed service, called by whichever app needs it, is what actually makes "one source of truth across independently deployed apps" true
- **Backend-for-Frontend (BFF) pattern, applied where it earns its keep, not uniformly**: `job-bank` and `employment-insurance` each get their own small dedicated backend (`job-bank-bff`, `employment-insurance-bff`) rather than storing their data in a shared in-memory lib. This is worth the extra services for exactly two apps because (a) it's the realistic shape of these systems in real life, and (b) it directly pays off the earlier "Job Bank must be reusable outside this shell" requirement — a standalone consumer needs its own real API behind the components anyway, not client-side mock state. `dashboard`/MSCA-D and `employment-life-events` don't get their own dedicated backends — there's no distinct bounded context there that justifies one
- MSCA-D's cross-benefit overview needs data that doesn't live in one place in real life — benefit eligibility, active job applications (owned by `job-bank-bff`), EI claim status (owned by `employment-insurance-bff`), profile/payments/correspondence (owned by `client-profile-service`), tasks. This is modeled as **`dashboard-bff`** — itself a BFF (specifically MSCA-D's), which calls the other three services over HTTP to compose its answer. Composition happens over real HTTP calls between services, not by importing another domain's in-memory state — that's what actually makes the independence claim true, not just a style preference
- `dashboard-bff`'s fan-out has an explicit partial-failure contract: each upstream call has a timeout, and a slow/failed one degrades only its own tile in the overview (with a visible "temporarily unavailable" state), not the whole response — this is both the correct resilience behaviour and a better demo moment than a blank page when a service is stopped
- On Firebase Hosting, since the static-baked-JSON fallback (below) is read-only but the core demo flow is a write (apply for a job/EI, then see it reflected), the hosted `<Domain>ApiClient` implementations are a **sessionStorage write-through over the baked JSON** — writes during the demo session are visible immediately without needing real compute on Firebase Hosting, using the same interface the local HTTP implementation satisfies
- Locally, each BFF is a small Node service (Nx-managed, e.g. Express/Fastify) served alongside its frontend; CORS between BFFs (and from frontends to their BFF) needs the same explicit handling as the frontend federation origins. On Firebase Hosting (static-only, no compute), the BFF-backed calls fall back to the same static-baked-JSON strategy already used for `ContentClient`/`RemoteRegistryProvider` — BFFs are fully real for the local demo, and stubbed for the hosted one, consistent with how the rest of the environment-swappable data layer works
- **Source control & CI/CD**: hosted on **GitHub** at `git@github.com:tn4consulting/mfe-pot.git`, CI/CD via **GitHub Actions** — each app gets its own workflow (path-filtered to its `apps/<name>/**` + shared `libs/**` it depends on) that lints/tests/builds/deploys only that app, using Nx `affected` to skip untouched apps; deploys run `firebase deploy --only hosting:<site>` per app, so merging a change to one MFE never triggers a deploy of the others
- **Local run**: a single orchestrated command brings up the whole environment (Strapi, the 4 BFF/service apps, and all 5 frontends, in that health-gated order) for an integrated demo, while every app remains independently runnable on its own (`nx serve <app>`) to prove independent deployability
- **Hosting**: **Firebase Hosting only**, and only as a stand-in static host — the eventual real target is not Google, so nothing here may depend on another Firebase product (no Firestore, Auth, Functions, or their emulators). Firebase project **`mfe-pot`** with **5 hosting sites**, globally-unique-name-prefixed (`mfe-pot-shell`, `mfe-pot-dashboard`, `mfe-pot-job-bank`, `mfe-pot-employment-insurance`, `mfe-pot-employment-life-events`), each independently deployable (`firebase deploy --only hosting:<site>`) with its own URL, mirroring the local independent-app story
- Since the 5 sites are 5 different origins, `firebase.json` needs explicit `headers`: CORS + `no-cache` on `remoteEntry.json`/`federation.manifest.json` (so a redeployed remote is picked up immediately, not served stale from Firebase's default caching), and `immutable` caching on hashed build chunks. Each remote also needs a build-injected absolute asset base URL (derived from `import.meta.url`) so its Transloco translation files and GCDS assets resolve against its own origin once embedded in the shell, not the shell's
- Since Firebase Hosting is static-only, it can't run Strapi. The hosted demo uses a third `ContentClient` implementation backed by **static, pre-baked EN/FR JSON** (exported at build time) instead of a live CMS. Strapi + its live `ContentClient` implementation stay a local-only dev/integration-test tool. Swapping which `ContentClient` implementation is active is purely environment configuration — the apps' code doesn't change between local and hosted

- Each MFE independently buildable, testable, deployable
- MFEs loaded dynamically at runtime via remote manifest — both full routes and shared widgets
- Angular is the preferred framework
- Recorded architecture decisions with rationale (Nx, Native Federation, Transloco, Strapi, Jest, Playwright, pnpm, shell-owned mock SSO, BFF-per-MFE pattern where valuable)
- Design/UX fidelity note: reference the real jobbank.gc.ca and canada.ca's public MSCA pages for look/feel/behavior, within GC design/accessibility limits, with the authenticated-MSCA-dashboard caveat spelled out explicitly so nobody mistakes the interior screens for a verified reproduction

- Keep a copy of planning documents (such as this one) in the repo at `docs/plans/`, filename prefixed `yyyymmdd-HHMM-` plus a meaningful name (e.g. `20260801-1420-mfe-pot-initial-design.md`) — these are project history/process artifacts, not citizen-facing content, so they're exempt from the docs EN/FR parity requirement

### 2. Nx workspace scaffold
- `git init`, initial commit, and `origin` set to `git@github.com:tn4consulting/mfe-pot.git`
- pnpm-based Nx workspace, Angular preset, standalone components, TypeScript throughout (including the BFF/service apps), ESLint with `typescript-eslint` + `angular-eslint` + Prettier
- `apps/shell` — thin host: app frame, GC header/footer, language switcher, mock login, federation manifest loader/router. Branded as the "My Service Canada Account" demo experience
- For each of the 4 MFEs, an `apps/<name>` thin federation host paired with `libs/<name>/feature-*` and `libs/<name>/ui-*` libraries holding the real functionality (see the packaging/DI-token decision above):
  - `apps/dashboard` (host, branded MSCA-D) + `libs/dashboard/feature-cross-benefit-overview` (eligible benefits, active applications, "my tasks" — powered by `dashboard-bff`), `feature-payment-history`, `feature-correspondence`, `feature-profile-maintenance` — the host wires the federation route table and exposes `./PaymentHistoryWidget` (sourced from `libs/dashboard/feature-payment-history`) for other remotes to consume
  - `apps/job-bank` (host) + `libs/job-bank/feature-search`, `feature-apply` — the concrete example of a library meant to be reused outside this shell entirely (the real standalone Job Bank site), so its public API can't assume this shell's DI wiring
  - `apps/employment-insurance` (host) + `libs/employment-insurance/feature-applications`, `feature-claims`, `feature-reporting` (submitting an EI report)
  - `apps/employment-life-events` (host) + `libs/employment-life-events/feature-guided-journey` — embeds `dashboard`'s payment-history widget live and deep-links into `job-bank` / `employment-insurance`
- BFF/service apps, each a small Node (Express/Fastify) app managed by Nx alongside the frontends: `apps/job-bank-bff`, `apps/employment-insurance-bff`, `apps/client-profile-service`, `apps/dashboard-bff` (calls the other three over HTTP to compose MSCA-D's overview)
- Each frontend talks to its backend through a thin `<Domain>ApiClient` interface (same environment-swappable pattern as `ContentClient`/`RemoteRegistryProvider`): local implementation calls the real local BFF over HTTP, Firebase-hosted implementation reads static baked JSON (no compute on Firebase Hosting), test implementation is in-memory
- One shared `apps/mfe-e2e` project (Playwright) covering the whole composed system (routed navigation across all 4 remotes, the widget-embedding proof, language switching, axe checks) — federation composition is only meaningful when tested composed, so that's where that investment goes
- Each app additionally runs its own standalone integration test target (Playwright against that app served alone, or Angular Testing Library-style harness), supplying stub implementations of the auth token, active locale, and remote-registry entries it would normally receive — this is what actually proves independent testability, distinct from (and smaller than) the composed suite
- `@nx/enforce-module-boundaries` lint rules with project tags (`type:app`, `type:shared-lib`, `scope:dashboard`, etc.) configured from the start, since preventing apps from reaching into each other is the actual mechanism behind "designed to split into separate repos later," not just a docs statement
- `libs/shared/ui-gcds` — Angular wrappers/helpers around GCDS web components (schema setup, GC header/footer, one shared page-layout primitive so 4 independently-built apps don't drift in spacing/heading levels). Bundled per app, not a federation singleton — so its custom-element registration must be idempotent, since two federated remotes both calling GCDS's define-elements on the same page must not throw on a duplicate `customElements.define`
- `libs/shared/i18n` — Transloco setup helpers (loader config, language-signal service the shell exposes and remotes subscribe to)
- `libs/shared/content-client` — CMS abstraction: `ContentClient` interface with three implementations — Strapi-backed (local dev/integration tests), in-memory stub (unit tests), and static baked-JSON (Firebase-hosted demo) — selected via environment config, not code changes
- `libs/shared/auth` — mock SSO token/DTO shape, token-parsing/validation logic, and a route-guard helper each app uses to enforce its own access checks against its own claims; bundled normally by each app (not a federation singleton), since it's stateless logic, not shared runtime state
- `libs/shared/remote-registry` — `RemoteRegistryProvider` interface plus Strapi-backed, static-JSON, and in-memory-stub implementations, resolving to the shared manifest shape (name → URL + route prefix + version). On a version mismatch between what the registry advertises and what a loaded remote reports, the shell logs a warning and loads it anyway rather than blocking — this is a demo/PoT tool, not a production compatibility gate
- `libs/shared/federation-runtime` — consumes `remote-registry` to mount routed remotes and dynamically import exposed widget components; owns failure handling for remotes that fail to load
- `libs/shared/testing` — MSW request handlers and fixtures shared across apps' integration tests

### 3. Native Federation wiring
- Native Federation configured on `shell` (host) and all 4 apps (remotes), each with its own `@angular-architects/native-federation` builder/dev-server config (this replaces, not extends, Nx's default Angular build/serve executors on these projects)
- `dashboard` exposes both a routed module and its one widget component; `employment-life-events` dynamically imports that widget to prove cross-remote component embedding
- Angular core + RxJS shared as singletons (required for widget embedding). Auth session and active-language state cross the remote boundary via a small versioned DTO + broadcast event, not a shared singleton library instance, to keep remotes decoupled enough to eventually live in separate repos
- Each remote exports `REMOTE_PROVIDERS`, applied at its own bootstrap and passed into the routes/component the shell mounts
- Remote discovery goes through a `RemoteRegistryProvider` abstraction (mirroring the `ContentClient` pattern) rather than the shell reading a static file directly — each entry carries name, URL, route prefix, and version. Three implementations, selected by environment config: **Strapi-backed** (local dev — edit a "Remote" entry in Strapi and the shell picks up the new URL/version on next load, no rebuild or restart, which is the actual portable-directory-server capability being proven), **static baked-JSON** (Firebase-hosted demo — Firebase Hosting can't run Strapi, so this is a file produced at deploy time, same constraint already accepted for CMS content), and **in-memory stub** (tests). The shell and `federation-runtime` only ever talk to the `RemoteRegistryProvider` interface, so which backing store is active is pure environment configuration
- Whichever implementation is active, it resolves to the same manifest shape (name → URL + route prefix + version), so the shell can construct/deep-link routes without knowing each remote's internal route structure ahead of time
- `federation-runtime` wraps every dynamic remote import in explicit failure handling so one remote/widget failing to load degrades gracefully (that route/widget shows an error state) instead of taking down the shell
- Manual verification: run shell + all 4 remotes on separate ports; confirm routed navigation into each app; confirm `employment-life-events` renders `dashboard`'s embedded widget with live (mocked) data; stop just one remote and confirm the others keep working, including the shell surfacing a graceful error for the stopped remote's route

### 4. Local headless CMS (Strapi)
- `docker-compose.yml` running Strapi locally with EN/FR locales enabled, demo content type(s) for page content across the 4 apps, and a **"Remote" content type** (name, URL, route prefix, version) acting as the local federation directory — seeded reproducibly via a committed `strapi export` archive imported on container start (not a manual/undocumented seeding step)
- `ContentClient` Strapi implementation over REST for page content; `RemoteRegistryProvider` Strapi implementation over REST for remote discovery; stub implementations of both for tests/quick local UI work without the container running

### 5. Testing setup
- Jest per app/lib via Nx's Jest preset, using MSW to stub HTTP calls in unit tests
- Playwright (in the single composed `mfe-e2e` project) uses its own `page.route()` interception to stub HTTP calls rather than browser-side MSW — avoids service-worker registration races across 5 origins — plus the local Strapi container for CMS coverage, including a dedicated test proving the widget-embedding scenario (`employment-life-events` renders `dashboard`'s live widget)
- `@axe-core/playwright` wired in so WCAG 2.2 AA checks run automatically
- Nx `affected` used so CI only builds/tests what changed

### 6. Local orchestration & Firebase Hosting
- A root script/target (e.g. `pnpm dev`, wired through Nx) with explicit startup ordering/health-gating: Strapi and the 4 BFF/service apps come up first (health-checked), then the 5 frontends — since `employment-life-events` and `dashboard` depend on those services being reachable — while `nx serve <app>` on its own still works for anyone iterating on a single MFE (or a single BFF) in isolation. A companion `pnpm demo:reset` restores Strapi and all 4 BFFs to known seed state for repeatable live demos
- `firebase.json` / `.firebaserc` defining **one Firebase project with 5 hosting sites** (`mfe-pot-shell`, `mfe-pot-dashboard`, `mfe-pot-job-bank`, `mfe-pot-employment-insurance`, `mfe-pot-employment-life-events`), each pointing at that app's Nx build output, each deployable independently via `firebase deploy --only hosting:<site>`
- The deployed federation manifest variant lists each app's Firebase Hosting URL; the local dev variant lists `localhost:<port>` per app — same manifest *shape*, different environment file
- Build config wires the **static baked-JSON** implementations of `ContentClient`, `RemoteRegistryProvider`, and all four `<Domain>ApiClient`s into the Firebase-hosted build (the BFF-backed ones via the sessionStorage write-through noted above, since that flow needs to support writes, not just reads), and the **Strapi-/BFF-backed** implementations of all of them into local dev builds — same swap mechanism, same constraint (no live backend on Firebase Hosting), applied consistently everywhere
- The shell's Strapi-backed `RemoteRegistryProvider` call has a timeout and falls back to a bundled default manifest if Strapi is slow or unavailable — Strapi sits on the shell's local boot path, so it must degrade gracefully rather than blocking startup entirely
- Explicitly out of scope / non-goals: Firestore, Firebase Auth, Cloud Functions, Firebase Emulator Suite for anything other than optionally sanity-checking the Hosting rewrite config itself — Firebase is a hosting stand-in only, so the design must not grow a dependency on any other Google service
- `.github/workflows/` — a single workflow that runs `nx affected --target=lint,test,build` on every push/PR, computes `nx show projects --affected --type=app` into a deploy matrix, and deploys each affected app to its own Firebase Hosting site on merge to main (plus a Firebase Hosting preview channel deploy on PRs). One workflow driven by `affected` avoids hand-maintained path filters per app drifting out of sync with actual dependencies; a separate job covers repo-wide checks (docs EN/FR parity, workspace-wide lint) that aren't tied to one app

## Demo Narrative & Experience

The architecture proves the MFE *pattern*; it doesn't by itself prove the *point* — that organizing around a life event (not separate benefit programs) makes the citizen's experience better and gets them back to work faster. That needs to be visible in minutes, not explained on a slide.

- **Siloed-mode toggle** in the shell (same apps, same BFFs) that disables the cross-service calls `employment-life-events`/`dashboard-bff` normally make — the citizen re-enters address/employer/bank details separately in `job-bank` and `employment-insurance` and sees three disconnected status pages. This is the "before" the whole demo argues against, and it's built almost entirely out of things already in the plan, just not wired together
- **A real "tell us once" demo beat**: address/bank details entered once in the `employment-life-events` journey visibly pre-fill the EI application and the Job Bank profile — actually crossing the `client-profile-service` boundary live, not just asserted as a capability
- **A visible policy-outcome proxy**: a simple journey meter (systems touched, fields re-entered, steps remaining, a simulated calendar day) that both modes feed — siloed mode shows job search starting on a simulated day ~24 (after EI processing), life-event mode shows it starting day 1 in parallel. This is what makes "people return to work faster" a picture instead of a claim

## Updates Since Initial Approval

The sections above are the original design as approved. What follows records material decisions and reversals made since, so this document stays a true record of intent rather than drifting from what `CLAUDE.md` (the current living summary) actually says. See `CLAUDE.md` for the authoritative current state; this section explains *why* it diverges from the plan above.

- **Docs bilingual requirement reversed for `docs/`.** The original plan called for mirrored `docs/en/`/`docs/fr/` trees with a parity check. Decision changed: `docs/` (contributor/process documentation) is English-only, since it's not a GC citizen-facing surface and doesn't carry the bilingual requirement the product UI and CMS content do. Bilingual EN/FR is still non-negotiable for everything the citizen sees — UI chrome (Transloco) and CMS page content (Strapi/`ContentClient`) — that part of the original plan is unchanged.
- **GC Design System package renamed.** `@cdssnc/gcds-components(-angular)` (named in the original plan) is deprecated/renamed to `@gcds-core/components` + `@gcds-core/components-angular`. All references in this repo use the new package names.
- **GCDS added to the federation-sharing singleton list.** The original sharing policy named only Angular core + RxJS as meeting the "large/stable/low-churn" bar. In practice, GCDS's Angular wrapper classes (`GcdsHeader`, `GcdsSignature`, etc.) are separate per-bundle classes even though the underlying custom elements are safely idempotent — without sharing, two federated bundles both defining their own copy trips Angular's `NG0912` component-ID-collision warning. `@gcds-core/components` and `@gcds-core/components-angular` are now shared singletons alongside Angular core + RxJS. The underlying policy (default to not sharing; only for dependencies where the coupling cost is clearly repaid) is unchanged — this is a second instance meeting that bar, not a policy change.
- **Zoneless change detection adopted.** Not mentioned in the original plan; the workspace now builds on Angular's zoneless change detection throughout, which has real implications for how component tests must be written (`fixture.whenStable()` doesn't track plain `fetch()`/promise chains — see `CLAUDE.md`'s Tooling section).
- **Native Federation implementation constraints discovered building it**, none anticipated in the original plan:
  - Cross-remote widget composition (the payment-history widget embedded in `employment-life-events`) turned out not to support remote-to-remote `loadRemoteModule` calls at all — each remote bundles its own disconnected copy of the Native Federation runtime, so a nested call from within a remote hangs forever. Fixed by making cross-remote widget loading host-mediated: the shell (which always has a working federation runtime) resolves the widget and hands the component class down via an injected DI token (`PAYMENT_HISTORY_WIDGET_LOADER`), rather than the consuming remote reaching across to another remote directly.
  - A plain Nx library must never import `@angular-architects/native-federation` directly — it can silently bundle its own disconnected copy of the package outside the builder's externalization, with its own `federationPromise` that's never resolved. Libraries now take `loadRemoteModule` via an injected `RemoteModuleLoader` token (`REMOTE_MODULE_LOADER` in `shared-federation-runtime`) instead.
  - The payment-history widget needed its `createComponent()` call paired with an explicit `environmentInjector` built from the widget's own providers (mirroring `RemoteRouteHost`'s pattern for routed remotes) — otherwise it silently ran in the *consuming* remote's injector, which has no idea what the widget needs. `PaymentHistoryWidgetLoader`'s return type changed from `Promise<Type<unknown>>` to `Promise<{ component, providers }>` to carry this.
  - Transloco needed two additional fixes for federated remotes that weren't anticipated: `TranslocoService` must be explicitly re-provided per environment injector (Angular's `providedIn: 'root'` default otherwise gives every remote the shell's singleton instance), and locale-sync must use `ENVIRONMENT_INITIALIZER` rather than `provideAppInitializer()`/`APP_INITIALIZER`, since the latter never fires for a child environment injector created via `createEnvironmentInjector` (how `RemoteRouteHost` mounts a remote).
  - Assorted build/dev-server gotchas now documented in `CLAUDE.md`'s Tooling section: `fileReplacements` doesn't swap copied `public/` assets (affects the hosted federation manifest); Vite/esbuild specially rewrites the exact inline `new URL('.', import.meta.url)` pattern, breaking origin computation unless split across two statements; bare workspace-library specifiers can't be imported from an app's own `main.ts` before Native Federation's import map exists; the Angular/Vite dev-server cache can serve stale compiled output for a `libs/` file consumed via a bare TS path-mapped import.
- **Monorepo → per-app repo split is now underway**, not just "designed to split later" as an abstract goal. Concretely: this repo becomes a platform repo (`libs/shared/*` published as versioned `@tn4consulting/shared-*` npm packages via GitHub Packages, plus `client-profile-service`, the composed `mfe-e2e` suite, and Strapi); 5 new per-app repos exist under the `tn4consulting` org, one per frontend, each carrying its own BFF(s) where it has one. `platform-versions.json` (repo root) pins the Angular/RxJS/GCDS/Node/TypeScript versions every app repo must stay aligned on, since Native Federation's shared-singleton contract breaks silently at runtime (no compile-time cross-repo warning) on drift. `@nx/enforce-module-boundaries` was tightened from a wide-open `sourceTag: '*'` rule to real per-scope constraints *before* extraction, specifically so a violation is caught as a one-PR fix rather than a cross-repo rewrite — this caught a real violation (`apps/shell` had a compile-time import into an `employment-life-events`-scoped lib), fixed by moving `PAYMENT_HISTORY_WIDGET_LOADER`'s token into the shared `shared-federation-runtime` package. Local multi-repo dev uses independent sibling clones tied together with a VSCode multi-root workspace file, deliberately not git submodules (`git worktree add` doesn't init submodule content, which would silently break this environment's own subagent worktree isolation).
- **Hosting is moving from Firebase to Kubernetes.** The original plan's Firebase Hosting design (5 sites, one per app, CORS/cache headers, static baked-JSON fallbacks) is accurate for today's *deployed* state but is being replaced: target is AKS + local k8s via Helm, with `docker-compose.yml` also being replaced. Not yet designed — Dockerfiles, chart shape (shared parameterized vs. per-repo, and a different shape needed for the Express BFFs), registry choice, and AKS access from CI are all open. Do not extend Firebase-specific tooling further without first checking whether this migration has already landed.
- **Known gaps carried forward, not yet closed**: the hosted build's BFF-backed `<Domain>ApiClient`s still have empty base URLs (the sessionStorage-write-through-over-static-JSON fallback described in the original plan isn't built yet — affected routes show "temporarily unavailable" or simply don't render on the hosted build); the 4 BFFs have no reset endpoint yet, so `pnpm demo:reset` (called for by the Demo Narrative section above) isn't built either, and the golden-path e2e test uses loose assertions to work around accumulating in-memory state; the payment-history widget still renders static English mock data, not yet wired to Transloco/locale-aware formatting.
